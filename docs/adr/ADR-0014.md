# ADR-0014: Modul compile-time + manifest + feature flag

## Konteks

Aplikasi akan bertambah fitur (C5.x, billing, notification, mobile).
Penambahan fitur harus mungkin TANPA mengubah inti keuangan (ledger).
Saat ini semua modul ter-compile bersamaan (compile-time import di
`AppModule`). Tidak ada mekanisme menyembunyikan fitur yang belum siap
dari user, dan tidak ada validasi dependensi antar-modul saat boot.

## Keputusan

**1. Modul compile-time dengan manifest:**
- Setiap modul NestJS punya manifest (`manifest.ts`) berisi:
  * `name` (e.g., "ledger", "billing")
  * `version` (semver)
  * `dependsOn: string[]` (modul lain yang harus ada)
  * `provides: string[]` (service yang diekspor)
  * `requires: string[]` (service yang dikonsumsi)
- Boot validation: `ModuleRegistry.validate(manifests)` — fail-fast bila
  ada dependensi yang hilang atau siklus.
- Modul baru butuh rilis (tidak hot-load).

**2. Feature flag (runtime):**
- Disimpan di tabel `settings` (existing) dengan key `feature.<name>.enabled`
- Decorator `@RequiresFeature("billing")` untuk endpoint/controller
- Resolusi: request → guard → query settings → allow/deny
- Bukan compile-time exclusion; endpoint tetap terdaftar tapi di-gate

**3. Modul baru butuh rilis:** tidak ada hot-load. Manifest compile-time
menjamin validasi dependensi di build, bukan runtime.

## Alternatif dipertimbangkan

1. **Plugin runtime dinamis** (hot-load modul tanpa restart) — ditolak:
   kompleksitas tinggi, keamanan (arbitrary code execution), tidak sesuai
   skala 2000-5000 customer.
2. **Feature flag murni tanpa manifest** — ditolak: tidak menangkap
   dependensi hilang (mis. billing butuh ledger, tapi ledger tidak ada).
3. **Monolith flat tanpa manifest** — ditolak: tidak scalable untuk
   C5.x + notification + mobile di masa depan.
4. **Microservices (deploy independen)** — ditolak: operasional terlalu
   berat untuk skala Fase 1 (2000 customer go-live, 5000 desain).

## Konsekuensi

**Positif:**
- Validasi dependensi di boot — gagal cepat
- Modul baru terisolasi sampai manifest + feature flag di-set
- "Inti keuangan" dilindungi dari drift (ledger manifest tidak dependsOn billing)
- Feature flag butuh satu guard tambahan — konsisten lintas modul

**Negatif:**
- Setiap modul butuh manifest (disiplin tambahan)
- Rilis untuk modul baru (tidak hot-load)
- Feature flag butuh query DB di request path (mitigasi: cache in-memory)

**Terikat dengan:** ADR-01 (modular monolith), ADR-07 (TypeScript monorepo),
ADR-16 (Ports & Adapters).

## Verifikasi implementasi

Struktur monorepo sudah modular (ADR-01 Diterima, ADR-07 Diterima).
Manifest + boot validation + feature flag belum diimplementasi —
dijadwalkan sebelum modul ke-5 dibuka. **Tidak memblokir C3** karena
`LedgerService` berfungsi tanpa manifest formal; ADR ini menetapkan
desain untuk modul-modul berikutnya.
